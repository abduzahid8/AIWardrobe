# Feedback, result reports and corrections

Reachable local client path: Profile → Report this result; BuyCheck result → Report this result; generated outfit card → Report this result. No prompt interrupts the core task. The user chooses feature, helpful yes/no, issue type and optional comment, then reviews exact JSON before opening the native share sheet. Closing/account switching discards the draft. No automatic screenshot, image, body-profile attachment or hidden reasoning exists. If a screenshot is needed, the user attaches it deliberately outside this text export. No destination or remote storage was configured.

Export schema v1 (`validationLoop.ts`): id, createdAt, appVersion, feature, helpful, issueType, optional comment (500 characters), diagnostics. Issues: wrong outfit, wrong fit, duplicate, irrelevant shopping, price issue, visual analysis wrong, slow, bug, confusing UX, privacy concern, other. Diagnostic allowlist: opaque requestId/traceId when actually available; ruleVersion; supported boolean featureFlags; low/medium/high confidence; bounded candidateCount; fallback enum. The local BuyCheck card includes confidence, evaluated count and local rule/fallback metadata; it does NOT invent a server request ID. Outfit/Profile can export without unavailable diagnostic fields. Do not claim all recommendations have trace correlation yet.

Optional correction reports cover garment type, color, fit, duplicate group, outfit context, product family and price match. Users enter previous/corrected values, review, and can undo while preserving before/after + revertedAt in the exported audit. This records an assertion for beta review; it does not silently edit shared products or train a model. Existing clothing details/Fit controls remain the direct product-edit paths. Corrections are session-local drafts, not a persistent repair ledger; export deliberately before closing if a durable local audit is wanted. Before/after/free comments may contain user-entered private text: the UI warns against it and nothing sends them automatically. Review/redact locally before sharing.

The optional createBetaEmitter adapter is versioned, strips undeclared properties at runtime, deduplicates concurrent IDs, bounds sent-ID memory and allows retry after sink failure. It is deliberately not connected to a new analytics destination. Test coverage: feedback diagnostics allowlist, correction undo, analytics sink failure/concurrency/dedupe, UI explicit choice/review/share and account reset. The existing analyticsService now allowlists properties, versions events, retains them on Edge errors, and only acknowledges the sent snapshot. No comment, correction values, raw images, URLs, body data or error-message text is allowed in that analytics payload. Unversioned legacy queue entries without event IDs are discarded rather than forwarding old unrestricted payloads. The prepared Edge analytics change preserves event IDs/schema and applies the same property allowlist; it has not been deployed. Existing event IDs support downstream dedupe; transport is at-least-once and the server/destination must deduplicate eventId to obtain exact event counts.

Local review: save voluntarily shared exports as JSON, then `npm run beta:review -- /absolute/path/export1.json /absolute/path/export2.json`. Arrays of records are also accepted. The script deduplicates IDs, reports failure/correction classes, repeated complaint categories and per-feature helpful/low-confidence/fallback shares. Positive feedback with the default other reason is not counted as a failure; an explicitly selected issue still counts. Timing p50 is the sample median, averaging the two middle values for an even sample count. It omits raw comments and identities. Report counts are selection-biased; they are NOT a feature usage ranking. Optional versioned observation records also summarize explicitly observed usage, exposed-but-unused complex features, timing groups, confirmed value/aha outcomes and versioned cost estimates. Without those records the corresponding fields remain null. Low-confidence/fallback rates use only reports where that diagnostic is known, not all reports. Do not replace null with zero.

For each weekly review answer with dated evidence and uncertainty:

1. Which feature drove the first confirmed value event?
2. Which feature drove a return on a later day?
3. Which impressive feature saw little use among users actually exposed to it?
4. Which feature repeatedly confused users?
5. Which feature costs most per successful value outcome, using observed rates?
6. Which premium feature do users explicitly say is worth paying for (and does purchase evidence agree)?
7. Which AI mistakes damaged fit, purchases, privacy or trust most?
8. Where did deterministic rules outperform AI on matched tasks?

No real beta users or answers are fabricated in this task. Collect corrections before adding speculative domains. User-selected comments/images require retention/access rules if the team later adopts a remote collector; that activation is outside this packet.

Optional local observation format is demonstrated in `observation-example.json` (SYNTHETIC ONLY). Each record has schemaVersion=1, unique id, kind=observation, feature and event. Supported events: feature_used; feature_exposed (usageInstrumented=true required before interpreting zero use); timing (latencyMs, measurementSource=device/simulator/host, device model label, buildType, boundary); outcome (outfit_saved, outfit_worn, buycheck_helpful, duplicate_avoided, missing_piece_confirmed, look_recreated_saved, fit_confirmed, return_to_plan, aha_confirmed); cost (amountMicros, currency, rateVersion). These are structures for locally supplied evidence, not newly enabled automatic event collection. Keep personal IDs, images, body data and raw comments out. Timing groups preserve source/device/build/boundary and cannot turn a host measurement into a device claim. No cost is fabricated when usage/rate evidence is missing. Use prospective observation windows and instrumentation coverage when comparing counts.

# BLUE TEAM FIELD MANUAL — Defensive Hackathon Cheat Sheet

Практический справочник для двухдневного defensive-хакатона: 5 защищаемых активов, атакующие на ногах, только Open Source, запрет на изменение исходного кода приложений, штрафы за простой сервисов.

**Проверено для:** Ubuntu 20.04/22.04/24.04, Debian 11/12, RHEL-семейство (с пометками). Wazuh 4.x, Suricata 6.x/7.x, Zeek 5.x/6.x, ModSecurity 2.9.x + OWASP CRS 3.3/4.x, nginx 1.18–1.26, fail2ban 0.11/1.0, nftables 1.0.x, iptables 1.8.x, auditd 3.x. Версии на месте сверяй командами вида `nginx -v`, `suricata --build-info`, `/var/ossec/bin/wazuh-control info`.

## 1. Правила соревнования → технические следствия

| Правило | Следствие | Что делаем |
|---|---|---|
| 5 отдельных активов | Нужна единая система наблюдения и одинаковый процесс на каждом активе | `recon.sh` на каждом хосте, общий logbook, одинаковый порядок настройки |
| Атакующие тестируют инфраструктуру | Блокировки должны быть с таймаутом и не задевать «валидаторов» | Баны 10–15 мин, `ignoreip`/allowlist для своего IP, всё блокированное — логировать |
| Только Open Source | Wazuh, Suricata, CRS, fail2ban, nftables, nginx — без коммерческих SIEM | Проверить наличие интернета на хостах до выбора стратегии установки |
| Флаги не дают очков сами по себе | Главное — защита, обнаружение и доказательства | Не гоняться за флагами в ущерб мониторингу; всё найденное фиксировать как доказательство |
| Нельзя менять исходный код | Защита — на уровне конфигов, сети, WAF, мониторинга | Не трогать файлы приложения; WAF, nginx, firewall, auditd — можно |
| Простой сервисов = штрафы | Любое изменение — с проверкой и откатом | Синтаксис до reload, поэтапное включение, health-проверки до/после (раздел 5 в [05-troubleshooting.md](05-troubleshooting.md)) |
| Полный сброс окружения = потеря прогресса | Всё должно быть воспроизводимо | Бэкапы конфигов + `git`-репозиторий конфигов + сохранённые логи вне хоста |
| День 2 — итоговая проверка | День 2 — стабилизация и демонстрация, не эксперименты | Все рискованные изменения — день 1; день 2 — только наблюдение и мелкие откаты |
| Финал: отчёт + бизнес-обоснование + презентация | Доказательства собирать с минуты 0 | Logbook, health.log, tar-архивы логов, метрики до/после (см. [04-reporting.md](04-reporting.md)) |

## 2. Матрица выбора инструментов

Стратегия для 2 дней: **сначала наблюдение (read-only, риск простоя нулевой), затем блокировка (обратимая), затем корреляция**. Не ставить всё подряд.

| Инструмент | Какую проблему решает | Для каких активов | Проверить перед внедрением | Ресурсы | Ограничения и риски | Проверка работоспособности | Проверка, что не ломает сервис | Приоритет |
|---|---|---|---|---|---|---|---|---|
| **Nginx** (reverse proxy, rate limit, заголовки) | Первый рубеж для HTTP: ограничение частоты, скрытие версии, запрет методов, защита админ-панелей | Любые HTTP-активы (если перед приложением уже стоит nginx/apache — настраивать его, не ставить лишний) | Перед кем стоит приложение (`nginx -T`, `ss -tlnp`), не занят ли порт, health-check приложения | Низкое (~десятки МБ RAM) | Неверный `proxy_pass` кладёт актив; `limit_req` может резать легитимных (шаред NAT); заголовки могут конфликтовать с CORS приложения | `curl` + запись в access.log; `limit_req` → 429 при флуде | `nginx -t` до reload; сравнить коды ответов и `time_total` до/после | ВЫСОКИЙ |
| **ModSecurity + OWASP CRS** | WAF: SQLi, XSS, path traversal, RCE-паттерны, file inclusion на уровне HTTP | Веб-активы и API | Пакет модуля под nginx/apache; путь CRS (`find / -name crs-setup.conf`); поддержка загрузки тела запроса | Среднее (CPU на regexp) | Ложные срабатывания режут легитимные запросы; мультипарт/загрузки; API с нестандартными методами | Тестовый SQLi-запрос → запись в `modsec_audit.log` | Начинать с `SecRuleEngine DetectionOnly`; сравнить 4xx/5xx до/после включения `On` | ВЫСОКИЙ (веб) |
| **nftables** | Сетевой фильтр: блоклисты с таймаутом, лимит новых соединений, прикрытие лишних портов | Все активы (Linux) | Какой firewall уже активен (firewalld/ufw/nft/iptables — только ОДИН менеджер!), не заблокирует ли SSH/health-check | Низкое | `flush ruleset` вытирает чужие правила; блокировка своего IP = потеря доступа; политика `drop` без готовых правил = простой | `nft list ruleset`; блок тестового IP с таймаутом | Отдельная таблица `bluelab` с `policy accept`; пинг/health-check после каждого правила | ВЫСОКИЙ |
| **Fail2ban** | Автоблокировка повторных неудачных входов (SSH, basic auth, rate-limit nginx) по логам | Хосты с SSH и веб-панелями | Где лежат логи (auth.log vs journal); `ignoreip`; версии фильтров | Низкое | Агрессивные jail банят легитимных и краулеров; systemd-системы без rsyslog требуют `backend=systemd` | `fail2ban-client status sshd`; ручной `banip` → разбан | `fail2ban-regex` перед включением jail; свой IP в `ignoreip`; баны ≤ 15 мин | ВЫСОКИЙ |
| **Suricata** (IDS) | Сетевая детекция: эксплойты, сканеры, SQLi на проводе, C2-паттерны, логи HTTP/DNS/TLS | Хост с зеркалом/входящим трафиком (edge) | Версия (`suricata --build-info`), HOME_NET = реальные CIDR, наличие правил (suricata-update или только local.rules без интернета) | Среднее-высокое (CPU/RAM на трафик) | IPS-режим (drop) опасен для доступности; в IDS ничего не блокирует — только видит | Тестовое правило + `curl -A blueteam-test` → запись в fast.log/eve.json | Работает пассивно — не влияет на сервис; проверить потребление CPU под нагрузкой | СРЕДНИЙ (но нулевой риск) |
| **Wazuh** | Централизованный SIEM: сбор логов со всех 5 активов, FIM, алерты, корреляция, единственное «окно» SOC | Все активы (агенты) + 1 хост-менеджер | Есть ли отдельный хост ≥ 2–4 ГБ RAM под менеджер; интернет для установки; время хостов (NTP) | Менеджер: 2–4 ГБ RAM, диск под индексы. Агент: минимальный | Менеджер «молчит» = нет обнаружений (проверять heartbeat); агенты — движение файлов, минимум изменений | `agent_control -l` (все агенты Active); тестовое событие → алерт в Dashboard | Агент read-only, риск нулевой; менеджер — на отдельном хосте | СРЕДНИЙ-ВЫСОКИЙ (если есть хост) |
| **auditd** | Локальный аудит: кто менял /etc, файлы, привилегии, execve | Все Linux-активы | Пакет auditd; объём событий (execve очень шумный) | Низкое | Не-рекурсивные watch на каталоги; перегруз правил = шум | `auditctl -l`; изменение файла → `ausearch -k identity` | Только чтение событий; правила `-w` на чтение метаданных не влияют на сервисы | СРЕДНИЙ (быстрая победа) |
| **iptables** | Как nftables, для старых ядер/дистрибутивов | Все Linux | Проверить, что нет конфликта с nft/ufw/firewalld | Низкое | Нет встроенных таймаутов банов; `-F` без бэкапа катастрофичен | `iptables -L -n`; правило → счётчик пакетов | Бэкап `iptables-save` до изменений; `--test` перед restore | ЗАПАСНОЙ (если нет nftables) |
| **Zeek** | Глубокий парсинг протоколов (conn, http, dns, ssl логи) | Edge-хост | Отдельная установка (нет в базовых репозиториях); время на изучение | Среднее-высокое | За 2 дня сложно настроить поверх Suricata; дублирует Suricata | `zeekctl status`; свежие логи в `/opt/zeek/logs/current/` | Пассивен — не влияет | НИЗКИЙ (только если время осталось) |
| **CrowdSec** | Альтернатива fail2ban: поведенческая детекция + баны (bouncers), сообщество IP | Хосты с SSH/веб | Интернет для hub; выбор bouncer (firewall) | Низкое-среднее | Не совмещать с fail2ban (двойные баны, путаница); нужна версия и настройки bouncer | `cscli decisions list`, `cscli alerts list` после тестового флуда | Свои IP в allowlist; короткие ban-таймауты | АЛЬТЕРНАТИВА fail2ban |
| **Docker/Podman мониторинг** | Видимость контейнеров: логи, состояние, ресурсы | Только если активы в контейнерах | Что контейнеризовано (`docker ps`), где compose-файлы, драйвер логов | Низкое (read-only) | `docker restart` = простой; json-логи растут бесконечно → полный диск | `docker ps`, `docker logs --tail`, `docker stats --no-stream` | Read-only команды безопасны; не пересоздавать контейнеры без нужды | ПО ТРЕБОВАНИЮ |

**Порядок внедрения в хакатоне (по возрастанию риска простоя):**
1. Бэкапы + baseline + health-проверки (риск 0).
2. auditd, логи, бэкап логов (риск 0).
3. Suricata в IDS-режиме на edge (риск 0 — пассивный).
4. nginx-хардненинг + rate limiting (риск низкий, тестировать поэтапно).
5. ModSecurity в DetectionOnly → CRS → `On` по одному vhost (риск средний, управляемый).
6. fail2ban с консервативными jail (риск низкий с ignoreip).
7. nftables-таблица `bluelab` (blocklist, лимиты) (риск низкий — изолированная таблица).
8. Wazuh-агенты, затем менеджер (риск 0 на активах).
9. Zeek/CrowdSec — только если осталось время.

**День 1, часы 0–1:** `recon.sh` на всех 5 активах, бэкапы, baseline-замеры, health-пробник, logbook.
**День 1, часы 1–4:** сбор логов и auditd, Suricata IDS, наблюдение — понять, куда идут реальные атаки.
**День 1, часы 4–8:** nginx-хардненинг, WAF (DetectionOnly → On), fail2ban, nftables-лимиты. Всё с тестами и откатами.
**Вечер дня 1:** архив логов, метрика «до», черновик отчёта, git-репозиторий конфигов.
**День 2, утро:** только стабилизация: мониторинг, минимизация FP, сверка метрик.
**День 2, после проверки:** финализация отчёта и презентации (см. [04-reporting.md](04-reporting.md)).

## 4. Что проверить в первые минуты (pre-flight)

На каждом активе ответить на вопросы (команды — в [01-quick-start.md](01-quick-start.md)):
1. Есть ли root/sudo? (`id`, `sudo -n true`)
2. ОС и версия? (`cat /etc/os-release`)
3. Какой firewall-менеджер активен? (`systemctl is-active nftables firewalld ufw`)
4. Что слушает порты? (`ss -tulpn`)
5. Есть ли контейнеры? (`docker ps 2>/dev/null || podman ps 2>/dev/null`)
6. Какие защитные инструменты уже стоят? (блок в `recon.sh`)
7. Есть ли интернет с хоста? (`curl -sI -m 5 http://deb.debian.org | head -1`)
8. Синхронизировано ли время? (`timedatectl status`) — критично для корреляции.
9. Где логи? (`ls /var/log`, `journalctl --list-boots | head`)
10. Что запрещают правила соревнования? (уточнить у организаторов ДО любых изменений)

## 5. 10 золотых правил (весь хакатон)

1. **Бэкап до изменения**: `cp -a file file.bak-$(date +%F-%H%M)` и tar-архив `/etc` на старте.
2. **Синтаксис до применения**: `nginx -t`, `nft -c -f`, `suricata -T`, `sshd -t`, `apachectl configtest`.
3. **Одно изменение за раз**, с проверкой health между изменениями.
4. **Никогда не блокируй**: свой IP, IP организаторов/валидаторов, health-check источники, 127.0.0.1.
5. **Reload, не restart** там, где возможно (nginx reload не рвёт соединения).
6. **Сначала пассивная детекция** (IDS, логи), потом активная блокировка.
7. **Баны с таймаутом** (10–15 мин) и с логированием.
8. **Не трогать** исходный код, порты приложений, systemd unit-файлы приложений без необходимости.
9. **Logbook всё**: время, что изменил, зачем, как откатить. Это потом = половина отчёта.
10. **День 2 — не экспериментируй**. Рискованное — в день 1, до финальной проверки.
